# AI Responsibility Reflection

## Limitations and Biases in the System

### The catalog is too small to represent real listener diversity

The recommender works from a hand-curated catalog of 18 songs. Each genre
appears only once or twice, which means the system has almost no ability to
distinguish between a casual fan and a deep listener within the same genre.
A lofi listener who prefers Japanese-style beats over lo-fi hip hop would
receive the same two results as every other lofi listener, because the catalog
has no way to express that distinction. In a real streaming platform, this
catalog size would represent about 0.000001% of available music — making any
recommendation practically meaningless.

### Genre weight creates a filter bubble

The genre feature carries a flat 2.0-point bonus for an exact match. That
number was chosen heuristically and never adjusted based on how listeners
actually respond to cross-genre recommendations. The effect, visible in the
Conflicted Edge Case test (TC-06), is that a profile asking for loud, intense
music will still receive a soft classical piece if the genre label matches —
because the genre bonus outweighs the energy mismatch. This is the same
mechanism that creates filter bubbles in production recommenders: once a
user's genre is inferred, the system keeps feeding them the same category
regardless of whether their other preferences are actually satisfied.

### Mood and genre labels are reductive

The system treats "happy" and "chill" as discrete, mutually exclusive
categories. Real listening experiences are more ambiguous. A person studying
might describe what they want as "focused but not boring" — a description
that does not map cleanly to any single mood tag. The label system also
encodes cultural assumptions about what genres sound like. Labeling a song
as "aggressive" or "moody" involves interpretive choices that different
communities might make differently, and those choices are baked invisibly
into the knowledge base.

### The knowledge base reflects one perspective

The descriptions in `music_knowledge.json` were written in one sitting by
one person working from a Western, English-language music framework. The
characterization of genres like hip hop ("centers on rhythmic vocals, culture,
and flow") or jazz ("warm and sophisticated") carries assumptions that are
not universal. A listener from a different cultural background might describe
those same genres in entirely different terms — and those terms would not be
in the knowledge base at all, leaving the RAG retrieval step empty-handed.

## Could This System Be Misused?

### Reinforcing stereotypes at scale

A music recommender seems low-stakes, but the same architecture — weighted
feature scoring, RAG context retrieval, AI-generated explanations — could be
applied to hiring decisions, loan approvals, or content moderation. The bias
mechanisms here (a dominant categorical weight that overrides other signals,
a static knowledge base written from a single viewpoint, discrete labels for
continuous human experiences) would cause serious harm in higher-stakes
domains. Building this system made those failure modes much easier to see,
which is part of why studying them in a low-stakes context matters.

### Generating confident-sounding but wrong explanations

The AI explanation feature can produce fluent, authoritative-sounding
recommendations even when the underlying confidence score is 0.59 — as
TC-06 showed. A listener who does not know how the system works has no way
to tell the difference between a 0.99-confidence explanation and a 0.59-confidence
one, because both are written in the same tone. This is a real misuse risk:
AI-generated text that sounds certain is not the same as text that is correct.

### Prevention steps built into this project

Several guardrails were implemented specifically because of these risks:

- **Confidence scores are computed and logged** for every recommendation so
  a reviewer can see when the system is operating outside its reliable range.
- **The fit evaluator is rule-based and deterministic**, not generated by
  Claude. This means the pass/fail verdict for a recommendation cannot be
  talked into by a well-phrased prompt.
- **The agentic loop is bounded** at eight iterations with an explicit exit
  condition, preventing runaway API calls or compounding errors.
- **Explanations cite sources** — the AI explanation references the retrieved
  genre/mood context rather than generating claims from scratch, making it
  easier to audit where a statement came from.
- **The evaluation harness uses labeled ground truth**, not self-reported
  quality. The system cannot grade its own output.

A further step not yet implemented would be to show confidence scores
directly to users alongside the explanation, so they can calibrate how much
to trust each recommendation.

## What Surprised Me During Reliability Testing

The most surprising result was how clearly TC-06 exposed a design flaw that
was invisible during development. The Conflicted Edge Case profile was not
designed as an adversarial test — it was just one of four profiles written
to explore edge cases. But when the confidence score made the result
quantitative (0.591 against an average of 0.882 for the other cases), it
immediately stood out as a failure that needed explanation, not just a
"weird result." Before adding the confidence metric, TC-06 would have passed
— the expected song was in the top 2 — and the flaw would have stayed hidden.

The second surprise was that TC-05 (Folk Nostalgic) passed at all. The
catalog has no song with both the `folk` genre and the `nostalgic` mood tag,
which meant the benchmark was asking for something impossible. The system
still found the closest available match (Porchlight Letters, folk + calm)
and ranked it first because the genre, energy, and acoustic features aligned
even without the mood match. That is actually correct behavior — returning
nothing because the perfect result does not exist would be worse than
returning the best available partial match. But seeing it score 0.773 instead
of failing entirely showed that the scoring math is more forgiving than the
labels suggest.

## Collaboration with AI During This Project

### One instance where the AI gave a helpful suggestion

When designing the evaluation harness, the initial plan was a simple pass/fail
test — either the expected song appeared in the top-k results or it did not.
The AI suggested adding a normalized confidence score (raw score divided by
theoretical maximum) so that the benchmark would distinguish between a
recommendation that barely squeaked into the top results and one that won
convincingly. That suggestion changed the most important output of the entire
evaluation section. Without confidence scoring, TC-06 would have shown "PASS"
and the genre-weight bias would have been invisible. With it, TC-06 showed
"PASS at 0.591" and the problem was immediately legible. A binary result
describes what the system did; a confidence score describes how well it did
it.

### One instance where the AI's suggestion was flawed

When building the system architecture diagram, the AI generated code that
used emoji characters as visual labels inside the diagram boxes — small icons
like a magnifying glass for the RAG component and a robot face for the Claude
agent. The code ran without errors but produced blank squares in the final
image because the default matplotlib font (DejaVu Sans) does not include
emoji glyphs. The AI did not catch this incompatibility before suggesting the
approach, and the first rendered diagram had empty placeholders where the
icons should have been. The fix was straightforward — replace emoji with
short text labels — but it required running the code, reading the warning
output, and recognizing that "Glyph missing from font" meant the emoji
approach would not work in this environment. The lesson is that AI suggestions
about rendering or environment-specific behavior should always be tested
before being trusted, because the AI does not have access to the actual
runtime and cannot predict font availability or library constraints.

## Summary

This project is a music recommender, not a hiring algorithm or a medical
diagnosis system. But the same three patterns that could cause real harm in
high-stakes AI — dominant categorical weights that override continuous signals,
static knowledge bases built from one perspective, and AI-generated text that
sounds confident regardless of underlying accuracy — are all present here in
miniature. Seeing them clearly in a low-stakes context is more useful than
studying them abstractly. The confidence score, the deterministic evaluator,
and the benchmark harness are not just technical features; they are the
habit of measuring what the system actually does rather than assuming it works
because it sounds right.
